# Agent Engineering Guide

This file is the entry point for every human or automated contributor.

## Priorities

Make trade-offs in this order:

1. **Usefulness** — solve a real, specified user problem.
2. **Correctness** — preserve data, report errors, and verify behavior.
3. **Performance** — optimize measured bottlenecks without weakening the first two priorities.

## Source of truth

- Product scope: `docs/specs/product.md`
- System boundaries and invariants: `docs/specs/architecture.md`
- Acceptance and quality gates: `docs/specs/quality.md`
- Active feature work: `docs/specs/README.md`
- Rust and GPUI rules: `.rules`
- Executable validation: `script/`

If implementation and specification disagree, do not silently choose one. Update the specification in the same change or explain why the implementation must remain unchanged.

## Work loop

1. **Orient:** Read the relevant specification, nearby code, tests, and recent Git history.
2. **Specify:** For non-trivial behavior, add or update acceptance criteria before implementation. State observable outcomes, failure behavior, and out-of-scope work.
3. **Plan:** Split work into independently verifiable steps. Identify correctness and data-loss risks first.
4. **Implement:** Make the smallest coherent change. Keep parsing and state logic independent from GPUI where practical so it can be tested without a window.
5. **Validate:** Run `script/quick` while iterating and `script/check` before declaring completion.
6. **Report:** Summarize behavior, tests, remaining risks, and any performance evidence. Never claim a check passed unless it ran successfully.

## Definition of done

A change is complete when:

- acceptance criteria are satisfied and linked to tests or explicit manual evidence;
- expected and malformed inputs are covered;
- user-visible failures are actionable and reach the UI;
- `script/check` passes;
- generated data, databases, traces, and profiler output are not tracked;
- documentation reflects changed behavior or architecture;
- performance claims include a reproducible baseline and comparison.

## Commands

- `script/bootstrap` — verify the required toolchain and fetch dependencies.
- `script/quick` — repository policy, formatting, and compile checks.
- `script/test` — the locked test suite.
- `script/clippy` — strict linting; use this instead of invoking `cargo clippy` directly.
- `script/check` — the full local/CI gate.
- `script/profile [database]` — profile into ignored `target/profiles/`.

All scripts are non-interactive, run from any working directory, and stop at the first failure.

## Specifications

Use `docs/specs/_template.md` for substantial features. Give requirements stable IDs such as `OPEN-001`; cite those IDs in tests, pull requests, and implementation plans. Keep status honest: `Proposed`, `Active`, `Blocked`, `Done`, or `Superseded`.

Do not mark a requirement done solely because code exists. It needs automated coverage where feasible, otherwise documented manual evidence and a reason automation is not practical.

## Repository hygiene

Profiling output belongs under `target/profiles/`. Test databases belong under `tests/fixtures/` and require an explicit exception in `.gitignore`; prefer fixtures generated by test code. `script/repository-check` rejects ignored tracked files, known profiler artifacts, and tracked blobs larger than 5 MiB.

Do not rewrite shared history or force-push unless the task explicitly requires it. When history is rewritten, publish with `--force-with-lease` and tell collaborators to rebase or re-clone.
